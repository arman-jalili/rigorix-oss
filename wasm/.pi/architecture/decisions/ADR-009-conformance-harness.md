# ADR-009: Conformance Harness — Live CLI Diff, Committed Goldens, and a Seeded Divergence That Must Fail

**Status:** Accepted
**Date:** 2026-11-03
**Session:** 3baf6e5c-e352-4127-af09-a5e7fe0a2d29

## Context

The crate's central claim is byte identity with the CLI for the same input (FR-007).
That claim is worthless if the comparison is approximate, if a missing vector counts as
a pass, or if there is no test proving the comparison can actually fail.

FR-011 (an additive `Clock` + `IdSource` seam reachable from the CLI) is measured
**false today**: there is no such input on the CLI, and the gate path reads
`Utc::now()` at 292 sites and mints identifiers at 37. So the harness must be honest
about being *blocked*, not quietly normalise timestamps and declare victory.

## Prerequisite Ordering (measured, not assumed)

The byte-identity claim depends on pinned inputs that **do not exist in this repository
today**: 292 `Utc::now()` call sites across the engine, 37 `Uuid::new_v4()` inside the
gate modules, no `Clock` trait, and no pinned-input flag on the CLI. FR-011 supplies
them.

Two rules follow, and they are the difference between a harness and a hope:

1. **A feasibility spike precedes Phase 0, not Phase 5.** Before the aggregate is built,
   prove three things in one branch: `rigorix-engine`'s gate slice compiles to
   `wasm32-unknown-unknown` behind the `portable` feature; a pinned clock produces
   identical envelopes twice on the CLI; and one envelope's bytes match between the CLI
   and the wasm build. Ten working days, and it fails *before* the crate is written
   rather than after four phases of it. The 292/37 inventory is the measured risk this
   spike retires.
2. **Criteria 19–22 cannot be marked complete before FR-011.** `normalised_comparison=true`
   is a *report label on a failing claim*, not a pass: while it is true, criterion 19 reads
   **blocked**, never **met**, and the roadmap shows the conformance phase as blocked in the
   same table it shows the others. When FR-011 lands the flag is deleted, and the deletion is
   the proof the claim changed status.

## Decision

**Three mechanisms, each with a different job.**

1. **Live CLI diff (authoritative).** CI builds `rigorix-cli` from the same commit,
   replays the vector through both runtimes with the same pinned clock/seed inputs, and
   compares artifact bytes. This catches drift the day a rule changes.
2. **Committed golden vectors (fast, hermetic).** Versioned scenario + fixture + clock
   files with their expected artifact bytes, used by the wasm-side test and the demo
   build. Regenerated by the live job; a stale golden fails the live diff rather than
   waiting for a human.
3. **Seeded divergence vector (the proof the harness works).** A vector whose fixture
   answer or serialization field is deliberately altered. The test asserts divergence,
   and **the test passes only when the comparison fails**. If the seeded vector stops
   diverging, the build fails — this is the guard against a comparator that silently
   compares nothing.

Rules:

- **No approximate comparison.** A nondeterministic field must be pinned, not stripped
  before comparison. ~~A normalised comparison may exist only as a labelled interim
  (`normalised_comparison=true` in the report) and must be deleted when FR-011 lands.~~
  **Withdrawn (ADR-014, #1367):** FR-011 was superseded, so the permission's precondition
  can never be true again, and the flag is refused outright — `wasm/ci/run-conformance.sh`
  fails a vector that sets it. A comparison that normalises anything compares the thing
  normalised, not the artifacts; the difference it would absorb is the one the oracle
  already measured (884 B unpinned vs 877 B pinned for the same decision).
- **A skipped or missing vector is a failure**, never a pass (FR-007).
- Vectors are immutable once committed; changing one is a reviewed artifact, not an
  edit-in-passing.
- The harness never ships: it is a `cfg(test)` + CI-only feature, absent from the wasm
  bundle (NFR-002).
- The report names which mechanism caught which divergence, so a red build is actionable.

## Consequences

### Positive
- The conformance claim is falsifiable in both directions: a real divergence fails, and
  a broken comparator also fails.
- Golden vectors give contributors a fast local loop without building the CLI.
- FR-011's absence is recorded as a blocking fact (labelled interim), not hidden.

### Negative
- CI must build the CLI (a few minutes) and hold the SDK token for the conformance job.
- Two mechanisms mean two failure surfaces to maintain. Accepted: they catch different
  classes of drift.

### Neutral
- Vector size is small (artifacts are JSON envelopes); no artifact store is needed.

## Alternatives Considered

| Alternative | Pros | Cons | Reason Rejected |
|-------------|------|------|-----------------|
| Goldens only | Fast, hermetic | Drift lands silently until someone regenerates | Stale-baseline failure mode |
| Live CLI only | Always current | Every run needs a CLI build; slow local loop; can't run in the demo | Needs a hermetic fast path |
| Semantic/JSON-equality comparison | Robust to key order | Hides exactly the byte-level drift that breaks verifiers | Defeats the claim |
| Normalise timestamps and ids | Unblocks the harness today | Makes "byte-identical" false while appearing green | FR-012 forbids it except as a labelled, temporary interim |
| Seed the divergence but skip assertion | Cheap smoke test | Proves nothing about the comparator | Kept as a real negative test instead |
