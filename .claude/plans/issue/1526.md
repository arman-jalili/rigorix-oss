# #1526 — a caller-supplied plan carries a dependency graph

## Implemented

- `TemplateStepDef.depends_on: Vec<String>` (`serde(default)`), naming other steps by `name`.
- `orchestrator/domain/step_graph.rs` — resolves names to step indices, and refuses the four ways a
  dependency set can be wrong, one variant each: `UnknownDependency` (naming the step, the missing
  name, **and** the known names), `SelfEdge`, `DuplicateStepName`, `Cycle` (naming the steps that
  remain plus what is behind them). `kind()` gives a stable string for callers that branch.
- `build_graph_from_steps` resolves first, then allocates one id per step in the caller's order and
  translates indices into edges. `run_from_template` and `plan_from_template` both go through it,
  since they share it.
- `OrchestratorError::InvalidStepDependencies { kind, detail }` — a caller can branch on `kind`
  instead of parsing a sentence.
- Order is Kahn's algorithm with the caller's list position as the tie-break, so the plan-time gate
  iterates the same order every run.
- MCP `plan_to_step_defs` passes `Vec::new()` and says why: the MCP plan template has no dependency
  concept, and empty keeps the sequential contract byte-identical.

## Two modes, stated because the difference is behavioural

No `depends_on` anywhere → the frozen sequential contract (step *n+1* depends on *n*). At least one
declared → dependency-driven, and a step with no dependencies has none. A mixed plan cannot be
half-sequential, so it is not.
