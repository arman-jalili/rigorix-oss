## Business Context

A universal gateway that bridges AI coding assistants to Rigorix's deterministic execution, audit, and policy enforcement capabilities via the Model Context Protocol (MCP). This enables any MCP-compatible AI tool to delegate execution actions to Rigorix — gaining audit trails, policy compliance, and deterministic replay without leaving their preferred interface.

### Core Principles

| Principle | Implementation |
|-----------|----------------|
| **Proxy architecture** | OSS handles protocol; enterprise capabilities proxied at runtime. Zero enterprise code in OSS binary |
| **Thin protocol layer** | MCP server adds no business logic — translates JSON-RPC to engine API calls |
| **Tool namespace isolation** | `rigorix_enterprise_*` tools discovered dynamically from enterprise server; unknown to OSS at compile time |
| **Read-only audit** | MCP audit tools are query-only. Audit immutability enforced by engine |
| **Template portability** | Templates created in any AI tool are accessible from all others via the shared MCP server |
| **Fail-safe proxy** | Enterprise proxy failures never cascade to OSS tools; clear diagnostic errors returned |
| **Transparent upgrade** | Same binary, same install. Adding enterprise = setting api_url + api_key in config |

### Strategic Value

1. **Distribution multiplier** — One MCP server works with all AI tools; Rigorix becomes the governance layer for the entire AI coding ecosystem
2. **OSS lead gen** — Free execution/audit/template tools are genuinely useful; enterprise features visible as upgrade path
3. **Cross-tool audit** — Enterprise aggregates audit across Claude, Cline, Cursor, etc. from a single MCP integration
4. **Competitive moat** — No other AI coding tool has a unified governance layer; Rigorix is the first

## Actors & Roles

| Actor | Description | Interactions |
|-------|-------------|-------------|
| **AI Coding Assistant** | MCP client (Claude Desktop, Cline, Cursor, Continue.dev, Aider, Copilot Codex) that connects to the MCP server to execute plans, read audits, and manage templates | Lists tools via `tools/list`, calls tools via `tools/call`, reads resources via `resources/read`, uses prompts via `prompts/get` |
| **Developer (User)** | Human software developer using an AI coding assistant. Sets up MCP config, provides natural language intent to the AI, reviews execution results and audit trails | Configures `rigorix mcp` in their AI tool's MCP settings, indirectly invokes Rigorix tools through the AI assistant during chat sessions |
| **Enterprise Admin** | Organization administrator who configures the enterprise proxy by setting `enterprise.api_url` and `enterprise.api_key` in rigorix config. Manages team policies and reviews cross-team audit data | Sets enterprise configuration, accesses enterprise-prefixed tools (team audit, approvals, policy management) through any AI tool |
| **Rigorix Engine** | Existing deterministic execution engine that actually runs plans, enforces policies, and records audit trails. The MCP server delegates all execution to this engine via EngineFacade | Receives plan execution requests, enforcement status queries, audit queries, and template operations from the MCP server's tool handlers |
| **Rigorix Enterprise Server** | Separate enterprise backend providing multi-team audit aggregation, approval workflows, policy management, and usage reporting. Accessed via the enterprise proxy | Receives proxied `rigorix_enterprise_*` JSON-RPC calls, authenticates via Bearer token, returns enterprise-specific results |
| **MCP Transport Layer** | The stdio or SSE connection substrate that carries JSON-RPC messages between the AI tool and the MCP server. Not a person but a protocol actor | Carries messages bidirectionally, manages connection lifecycle, handles stream errors |

## Assumptions

| Assumption | Impact if Wrong | Mitigation |
|------------|----------------|-----------|
| AI coding tools implement MCP client side correctly per spec | Tools fail to connect or list tools incorrectly | Test against Claude Desktop, Cline, Cursor, Continue.dev, Aider during Phase 4 |
| Users run MCP server on the same machine as their AI tool (localhost for SSE, same process for stdio) | Network latency or security issues for remote setups | Document localhost requirement; SSE bind address configurable |
| Users have rigorix-engine installed and configured before using MCP tools | Tools return "engine not available" errors | Clear error messages pointing to install/setup docs |
| Enterprise API is reachable via HTTPS from the MCP server machine | Enterprise tools fail with connection errors | Clear error messages; OSS tools unaffected |
| Template files are valid TOML and follow the schema | Template parsing fails with unclear errors | Validate on read and write; return structured validation errors |
| AI assistants respect tool schemas and send valid arguments | Tools return "invalid arguments" errors | Schemas are precise; errors guide AI to correct format |
| Multiple AI tools can connect to the same MCP server simultaneously | Resource contention or session conflicts | Session isolation; stateless tool handlers |
| Enterprise API version is forward-compatible with proxy protocol | Schema negotiation fails; enterprise tools unavailable | Version negotiation during initialization |

## Resolved Decisions

| # | Question | Decision | Rationale |
|---|----------|----------|-----------|
| 1 | Separate binary or CLI subcommand? | Both: `rigorix mcp` subcommand in CLI crate AND standalone `rigorix-mcp` binary sharing the same code. Subcommand for user discovery, standalone binary for MCP config files in AI tools that need an executable path. | Best discoverability + widest compatibility |
| 2 | Progress notifications for long executions? | Use MCP `notifications/progress` for SSE transport. Omit progress for stdio (output is consumed synchronously by the parent process; progress messages would interleave with tool responses). | stdio is inherently synchronous; SSE can stream |
| 3 | SSE transport library? | `axum` | Ecosystem compatibility, mature, widely used in Rust |
| 4 | MCP Rust library? | Hand-rolled JSON-RPC over stdio (~200 lines) for Phase 0. The MCP protocol is simple (initialize, tools/list, tools/call, resources/read, prompts/get). No external MCP SDK dependency means zero risk of upstream breakage. Can adopt an SDK later if one stabilizes. | Minimal dependencies, full control, simple protocol |
| 5 | Template storage interaction with enterprise? | **Alternative A: Local filesystem only** for OSS tools (`rigorix_list_templates`, `rigorix_create_template`). Enterprise templates are separate `rigorix_enterprise_*` tools proxied to the enterprise API. No cross-contamination. The two template worlds never touch. | Cleanest boundary, no sync logic, enterprise evolves independently |
| 6 | Schema fetch: lazy or eager? | Eagerly fetch enterprise tool schemas during proxy initialization. If the fetch fails, enterprise tools are unavailable with a clear error. Schemas are cached for the server lifetime. | Simple initialization, reliable capability negotiation, no cold-start latency on first enterprise tool call |
